## 2. Diseño

### 2.1 La función

**Nombre:** `public.audit_log_create_partition(integer) RETURNS boolean`. Devuelve `true` si la ha creado y `false` si ya existía.

- **Propietario:** el rol de migración. La crea la migración, que corre con `pgsql_migrator`.
- **`EXECUTE`:** solo el rol de aplicación. `REVOKE ALL … FROM PUBLIC`; mantenimiento no lo recibe.

Cuerpo de referencia. Las marcas `:x:` se sustituyen con `strtr`, igual que en `dropFunctionStatements()`:

```sql
CREATE OR REPLACE FUNCTION public.:function:(p_year integer)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, pg_temp
SET lock_timeout = '5s'
AS $kronoqr$
DECLARE
    utc_year       integer := extract(year FROM (now() AT TIME ZONE 'UTC'))::integer;
    partition_name text    := ':table:_' || p_year::text;
    existing       oid;
BEGIN
    IF p_year IS NULL OR p_year < :first_year: OR p_year < utc_year OR p_year > utc_year + 1 THEN
        RAISE EXCEPTION 'Ano de particion fuera de rango: %', p_year USING ERRCODE = '22023';
    END IF;

    IF EXISTS (SELECT 1 FROM public.:anchors: WHERE partition_year = p_year) THEN
        RAISE EXCEPTION 'El ano % esta sellado: no se recrea su particion (ADR-027)', p_year
            USING ERRCODE = '22023';
    END IF;

    PERFORM pg_advisory_xact_lock(hashtext('kronoqr.:function:'));

    SELECT c.oid INTO existing
      FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
     WHERE n.nspname = 'public' AND c.relname = partition_name;

    IF existing IS NOT NULL THEN
        IF EXISTS (SELECT 1 FROM pg_inherits
                    WHERE inhrelid = existing AND inhparent = 'public.:table:'::regclass) THEN
            RETURN false;
        END IF;
        RAISE EXCEPTION 'public.% existe y no es particion de :table:', partition_name
            USING ERRCODE = '42P07';
    END IF;

    EXECUTE format(
        'CREATE TABLE public.%I PARTITION OF public.:table: FOR VALUES FROM (%L) TO (%L)',
        partition_name, p_year || '-01-01T00:00:00Z', (p_year + 1) || '-01-01T00:00:00Z'
    );
    -- :grants: — generado desde la misma fuente que appendOnlyGrantStatements() (§2.2)
    RETURN true;
END;
$kronoqr$
```

Seguido de:

```sql
REVOKE ALL ON FUNCTION public.:function:(integer) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.:function:(integer) TO "<rol de aplicación>";
```

**Por qué cada pieza:**

| Pieza | Motivo |
|---|---|
| Parámetro `integer` y `format('%I')`/`%L` | No entra texto de quien llama. Solo puede nacer `public.audit_log_<año>` como partición de `public.audit_log`. Las fechas llevan `Z`, así que no dependen de la zona horaria de la sesión (regla dura 3) |
| Rango `[año UTC, año UTC + 1]`, sin bajar de `FIRST_YEAR` | Cubre el caso correctivo (año en curso) y el preventivo (año siguiente desde noviembre). Si el reloj de PHP va por delante del de la base en Nochevieja, pide +1, que está admitido; si va por detrás, el año en curso ya existe |
| Rechazo de años con ancla | Un año purgado (ADR-027) no puede reaparecer vacío. Permitiría escribir entradas retrodatadas en un año que el verificador da por cerrado |
| `search_path = pg_catalog, pg_temp` y todo calificado con `public.` | El propietario es SUPERUSER. Si `pg_temp` no aparece explícito y al final, PostgreSQL lo busca **primero** para las relaciones, y `PUBLIC` tiene `TEMPORARY` sobre la base: un `CREATE TEMP TABLE audit_log` del rol de aplicación podría desviar la resolución |
| `pg_advisory_xact_lock` | Dos llamadas simultáneas no chocan con `42P07`. El planificador ya tiene `withoutOverlapping()`, pero la función no debe depender de ello |
| Excepción ante una tabla homónima que no es partición | Cierra el hueco silencioso de `IF NOT EXISTS` |
| `lock_timeout = '5s'` | `CREATE TABLE … PARTITION OF` pide un bloqueo exclusivo sobre `audit_log`, y los fichajes que escriben auditoría harían cola detrás. Mejor que la tarea falle y se reintente al día siguiente (hay dos meses de margen) |
| Índices y restricciones | La PK `(id, occurred_at)`, los `CHECK` (`2026_08_19_101500_create_audit_log_table.php:72-95`) y los índices particionados (`:123-137`) se propagan solos a toda partición nueva. No se repiten, pero la prueba los comprueba |

### 2.2 Permisos de la partición nueva: una sola fuente

- Dentro de una función `SECURITY DEFINER`, `current_user` es el propietario de la función, así que la partición **nace propiedad del migrador**, igual que las demás.
- **Trampa:** los `ALTER DEFAULT PRIVILEGES` de `2026_08_19_099000_provision_database_privileges.php:57-64` los ejecutó el migrador y también se aplican a lo que cree la función. Sin los `REVOKE`, la partición nacería con `UPDATE` y `DELETE` para la aplicación.

**Refactorización obligatoria de `AuditLogSchema::appendOnlyGrantStatements()`** (`AuditLogSchema.php:175-188`), para que la migración antigua y el cuerpo de la función salgan de la misma lista:

1. Nuevo método privado `appendOnlyGrantTemplates(): list<string>` que devuelve las cinco sentencias con la marca `{relation}` en lugar del nombre de la tabla y los roles ya entrecomillados con `quoteIdentifier()`. Por ejemplo, `REVOKE ALL ON TABLE {relation} FROM PUBLIC` y `GRANT INSERT, SELECT ON TABLE {relation} TO "fichaje_app"`.
2. `appendOnlyGrantStatements(string $relation)` sustituye `{relation}` por `self::quoteIdentifier($relation)`. **La salida no cambia**: la usan `createPartitionStatements()`, `2026_08_19_101500_create_audit_log_table.php:110` y, si procede, la migración de anclas.
3. `createFunctionStatements()` genera `:grants:` sustituyendo `{relation}` por `public.%I` y envolviendo cada plantilla en `EXECUTE format('<plantilla>', partition_name);`. Las plantillas no contienen `'` ni `%` porque `assertIdentifier()` (`:213-223`) solo admite `[A-Za-z0-9_]`. Hay que dejarlo dicho en un comentario y cubrirlo con una aserción en PHP que lance una excepción si aparecieran.

Con eso, el rol de aplicación gana únicamente `EXECUTE` sobre la función. No gana `CREATE` en el esquema, ni propiedad, ni `UPDATE`, `DELETE`, `TRUNCATE`, `DETACH` o `DROP`.

- Constante `public const string CREATE_FUNCTION = 'audit_log_create_partition';` junto a `DROP_FUNCTION` (`:34`), con el mismo comentario de por qué vive aquí.

## 4. Pruebas

Toda prueba nueva va etiquetada con `->group(...)` (RQ-13). **Los años se calculan desde el motor** (`SELECT extract(year FROM now() AT TIME ZONE 'UTC')::int`), no con `FixedClock`, porque la ventana de la función usa el reloj de PostgreSQL.

### 4.0 El patrón de las pruebas de base de datos: una transacción del propietario con `SET LOCAL ROLE`

**El problema:** tras `migrate:fresh`, las particiones `y` e `y+1` ya existen: las crea `create_audit_log_table.php:153-165` y las vuelve a asegurar el paso 2 de la nueva migración. La ventana de la función es exactamente `{y, y+1}`, así que desde la conexión de aplicación solo se podría probar el `false` idempotente. Soltar `y+1` confirmando el cambio contaminaría la base compartida, y **`CommittedDatabase` no sirve**: su docblock la reserva a las pruebas de concurrencia.

**La solución:** es el mismo recurso que ya usa `AuditLogTest.php:245-297` para simular al atacante. Todo ocurre en **una transacción de la conexión de migración que se deshace al final**. El DDL de PostgreSQL es transaccional.

1. `SET LOCAL lock_timeout = '5s'`, para que una espera de bloqueo falle en vez de colgar la suite.
2. Como propietario: `ALTER TABLE audit_log DETACH PARTITION audit_log_<y+1>` y `DROP TABLE audit_log_<y+1>`, o cualquier otra preparación (anclas, tablas homónimas, `DROP FUNCTION`).
3. `SET LOCAL ROLE "<rol de aplicación>"`. A partir de aquí PostgreSQL comprueba los privilegios contra `fichaje_app`, incluido el `EXECUTE` de la función, y la función `SECURITY DEFINER` cambia al propietario solo durante su ejecución.
4. Se ejecuta lo que se prueba y se comprueba el catálogo.
5. `ROLLBACK`.

Hay que crear un ayudante en el fichero de prueba, por ejemplo `comoAplicacionEnTransaccionDelPropietario(Closure $preparar, Closure $probar)`. **No se consulta `audit_log` por la conexión por defecto** antes de abrir esa transacción en la misma prueba: el `DETACH` esperaría a ese bloqueo.

Para las pruebas del **comando** (11 y 12), que resuelven el adaptador sobre `DB::connection()`, se usa la misma transacción sobre un **clon de la configuración de `pgsql_migrator` con otro nombre** (`pgsql_owner_as_app`), registrado con `Config::set`:

- `DB::setDefaultConnection('pgsql_owner_as_app')` y `app()->forgetInstance(AuditLogPartitions::class)`;
- después se inutiliza `pgsql_migrator` (host `203.0.113.1`, contraseña falsa y `DB::purge`).

Así queda demostrado lo que importa: el comando **no nombra** `pgsql_migrator` y funciona **con los privilegios del rol de aplicación**. Al terminar se restaura la conexión por defecto.

### 4.1 Nuevas

**`backend/tests/Integration/Compliance/AuditLogPartitionFunctionTest.php`**, `->group('RS-07', 'RL-04')`. Los casos 1 a 8 y 10 siguen el patrón de §4.0; el 9 solo lee el catálogo.

1. `crea con el rol de la aplicacion la particion del año siguiente, adjunta y con sus limites`. Se prepara soltando `audit_log_<y+1>` y la función devuelve `true`. `pg_get_expr(relpartbound, oid)` contiene `'<y+1>-01-01 00:00:00+00'` y `'<y+2>-01-01 00:00:00+00'`.
2. `la particion nueva es del migrador y tiene los mismos permisos que audit_log_2026`:
   - `relowner` es el rol de `database.roles.migration`;
   - `relacl` es igual a `audit_log_2026`;
   - `has_table_privilege`: la app tiene `INSERT`/`SELECT` y no `UPDATE`/`DELETE`/`TRUNCATE`; mantenimiento solo `SELECT`.
3. `la particion nueva hereda los indices y las restricciones de la tabla madre`. Mismo número de índices (`pg_index` sobre la partición) y mismos `CHECK` (`pg_constraint` con `contype = 'c'`) que `audit_log_2026`.
4. `es idempotente`. La segunda llamada devuelve `false`, sin error.

## 5. Riesgos

| Riesgo | Tratamiento |
|---|---|
| **Instalaciones existentes** | Las instaladas en 2026 ya tienen las particiones de 2026 y 2027 (`create_audit_log_table.php:153-165`), y el paso 2 de `up()` asegura el año en curso y el siguiente al actualizar. El primer uso real de la función será en noviembre de 2027 |
| **Migración sin atribuir en la matriz de versiones** | `update.sh:1718` aborta la actualización antes de levantar el runtime nuevo. Se ve en el job ⑧b y en la actualización 2.1.0 → 2.2.0 en dind (**devops**) |
| **Vuelta atrás con `update.sh`** | Se restaura la copia: la función desaparece con ella y el código 2.1.0 vuelve a usar `pgsql_migrator`, que sigue en el `.env`. Es coherente, pero **reabre AUD-1** hasta volver a la 2.2.0, y el informe de la actualización debe decirlo. Hay que comprobar que se restaura también el `compose.prod.yaml` de la 2.1.0 |
| **La función falta porque la migración no se aplicó** | El planificador falla con `Log::critical('audit_log_partition_creation_unavailable')` y un mensaje que nombra la migración, y la métrica queda a 0: suena el aviso (desde noviembre, 6 h) o la crítica (año en curso). **El fichaje no se bloquea** mientras exista la partición del año en curso |
| **Contención de bloqueos** | `lock_timeout` de 5 s en la función y ejecución a las 02:45 UTC. El peor caso es una tarea fallida que se reintenta al día siguiente, no fichajes en cola |
| **Pruebas con reloj fijo en otro año** | Una prueba de integración que use `FixedClock` en un año distinto del de la base será rechazada por la ventana (`22023`). Los años se calculan desde el motor. Las unitarias no se ven afectadas |
| **El propietario de la función es SUPERUSER** | Se asume mientras el migrador sea el rol de arranque (ADR-033, ADR-042). Por eso la función es mínima, recibe un `integer` y califica todo. La evolución es un rol propietario `NOLOGIN`, fuera de la 2.2.0 |
| **Cambio de nombre de rol después de migrar** | Los roles quedan grabados en la función al crearla, igual que en la de purga. Si cambian `DB_USERNAME` o `DB_MAINTENANCE_USERNAME`, hay que volver a lanzar la migración (queda dicho en ADR-042) |
